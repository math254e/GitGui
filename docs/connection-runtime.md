# Connection runtime

GitGui's client runtime is T3 Code's client runtime, adapted to Git. This
document describes the runtime as it exists here. The vendoring rules, the
upstream snapshot, and the per-file divergences live in
[t3code-vendoring.md](./t3code-vendoring.md).

## Environment names

Connections settings accepts an optional name during direct and SSH setup and
offers Rename for every registered environment, including the automatic primary
and disconnected environments. Blank setup names use the server's plain machine
label; a generic `This computer` label uses the direct endpoint hostname or SSH
alias instead. Rename requires a nonempty name, trims surrounding whitespace,
and rejects control characters and names longer than 512 characters.

Names are client preferences keyed by the backend-issued EnvironmentId. Electron
persists them in its existing state file through a narrow typed name capability;
the browser stores them under `gitgui.environmentNames.v1`. They contain no
connection credential. They survive descriptor refreshes, reconnects and restarts,
and explicit environment removal clears them with other client-owned data.
Naming never changes IDs, routes, credentials, selection, tabs, caches, the live
RPC generation, repository files or the Git index. It requires no server request.

The current T3 checkout's onboarding `label` input and target/profile labels are
used during setup. A separate client name preference is a deliberate GitGui
translation: the primary is platform-owned and environments can have several
routes, so editing a presentation name must not replace an active supervisor or
require an invented server rename RPC. The preference wins over every route's
label. It does not rename the environment for other clients or change the server
descriptor. Primary setup is automatic; its name is edited in the environment
list after discovery.

New server descriptors use a plain host-derived default. Following T3's
`ServerEnvironmentLabel`, Linux prefers `/etc/machine-info`'s pretty hostname;
GitGui then reads the kernel hostname instead of spawning `hostnamectl` on
descriptor requests. Windows uses the machine-name environment value. These
defaults never replace an explicit client name.

Existing registrations and encrypted credentials need no migration or re-pairing.
Without an explicit preference, only the legacy `GitGui on <single-word host>`
and `GitGui on This computer` forms are recognized as autogenerated defaults and
displayed without the prefix. Other existing custom labels are retained. An old
name deliberately matching that historical default cannot be distinguished from
an autogenerated name; saving it explicitly with Rename preserves it verbatim,
including a product prefix if desired. Normalizing an old default never records
it as an intentional user rename or rewrites the saved registration.

Name writes publish only after persistence succeeds. A failed rename retains the
current name and leaves the edit open. Setup commits the authenticated connection
before the optional name preference; if that second write fails, the UI reports
that the environment connected and directs the person to retry Rename. Browser
names are scoped to its origin/profile; desktop names use the existing application
state directory. Names are read at startup, so another already-open client window
observes a rename after reload rather than through a new synchronization service.

## Concurrent request lifetime

The session correlates responses by request ID; independent reads may finish
out of order. Pending registration and cleanup are protected from interruption.
Timeouts and caller interruption remove the pending entry and, when the welcome
advertises `rpc.cancel`, send `{ "type": "cancel", "id": "request-…" }`.
Older protocol-v2 servers receive no cancellation notification. This is an
additive capability, so the protocol version remains 2.

Cancellation belongs to the current socket and applies only to read methods.
The server answers a cancelled read's original ID with `request_cancelled`;
missing, completed, repeated, and mutation cancellations are ignored. Late
responses cannot complete another call. The Promise bridge accepts an
`AbortSignal` for file diffs and hunk previews and interrupts their Effect calls.
The viewer aborts both requests when selection changes or it is destroyed.
Session termination fails all pending calls and sends no cancellation frames.

The Rust socket loop keeps reading frames and events while dispatches execute.
Each session admits at most 128 pending/running requests, with eight independent
reads, eight repository operation lanes, one prefetch, and one control request
able to run concurrently. Operation lanes preserve arrival order per repository,
including working-tree file diffs that prepare hunk continuations and lock-sensitive
hunk/discard/amend previews. Ordinary file diffs remain independent reads. The existing server-wide
repository mutex still serializes operations from different sessions. Ordering
between different sockets is determined by that mutex, not a global wire order.
Read snapshots retain their existing semantics when another session mutates.

Overload returns `server_busy` without closing the socket. Reusing a pending or
running ID returns `duplicate_request_id`; clients must keep IDs unique for
the session. Parse failures, scope checks, Git errors, binary JSON, and event
delivery continue through their existing protocol paths.

Cancellation removes queued reads immediately. Started dispatches retain their
slots and repository guards until completion, and their late responses are
suppressed. Disconnect drops queued work and detaches started dispatches so a
live blocking worker cannot lose its lock. A mutation already dispatched may
complete after disconnect; clients must revalidate rather than replay it.

Commit-diff hints retain the one-target protocol limit from issue #7. File-list
hints validate every supplied hash but process at most one. Both report the
number actually processed in `count`. Their separate slot keeps a
large hint out of the interactive read queue. Only one additional hint may
wait; excess hints receive `server_busy` so prefetch cannot fill session
admission capacity. This deliberately trades cache
warming for bounded work; choosing which target to warm remains GitGui policy.
Git subprocesses still have no cancellation/deadline support: up to eight
already-started obsolete reads per session can delay further reads until a
worker finishes. This change bounds their count, not their execution time.

Regression coverage lives in `rpc/session.test.ts` and the server's
`rpc_queue.rs`/`rpc_tests.rs`, including out-of-order errors, aborts/timeouts,
late replies, bounded admission, mutation order, and a disconnect during a
blocked pre-commit hook.

## One transport retry owner

The [supervisor](../packages/client-runtime/src/connection/supervisor.ts) owns
transport retry policy; resolving an endpoint and opening an RPC session are
single attempts. Transient failures retry with jittered exponential backoff,
capped at five minutes, that resets only after a connection stays up. Without
jitter, every client of a restarted server reconnects in the same second; with
a short cap, a client that can never connect retries all day. Offline states
and authentication failures wait for a wakeup instead of spending attempts on
unchanged conditions.

Foregrounding, an explicit retry, and an offline report probe the established
session, and only a failed probe reconnects. Offline reports are often wrong,
for example for a loopback server. Foregrounding also wakes a pending retry
immediately and leaves an ordinary in-flight attempt alone.

The [registry](../packages/client-runtime/src/connection/registry.ts) scopes
connections by environment. An involuntary disconnect retains the registration
and cached data. Explicit removal closes the scope and clears credentials,
projections, and platform-owned state such as drafts.

Platform discovery follows T3's catalog polling pattern: it refreshes every
three seconds and on foreground/online signals. Discovery failures are typed
and leave the last successful registration intact; an initial failure can
recover before any supervisor exists. Port changes replace the primary target,
while unchanged discovery does not replace a healthy supervisor. An explicit
desktop restart installs the prepared endpoint immediately. This catalog
refresh does not open sockets or own transport retries.

## The layers

```text
EnvironmentRegistry
  -> EnvironmentSupervisor
     -> ConnectionDriver
        -> ConnectionResolver
        -> RpcSessionFactory
```

- The backend-issued `EnvironmentId`, not a URL hash, identifies an
  environment.
- The resolver prepares endpoint and authentication information.
- The driver and the session factory perform one attempt and never retry.
- The supervisor is the only retry owner.
- Transient failures retry indefinitely with capped backoff.
- Auth, permission, invalid configuration, and incompatible protocol failures
  block until external state changes.
- Offline state releases transport without consuming retry attempts.
- Foreground and wakeup probes active sessions.
- A replacement session advances an environment generation.
- Queries revalidate, subscriptions switch, and mutations resolve the current
  session after a generation change.
- Explicit environment removal disposes registration, credentials, session,
  supervisor, cache, and client workspace state.

## The GitGui envelope

The GitGui server is Rust and speaks the GitGui JSON envelope. A session
multiplexes three message kinds over one WebSocket:

- `welcome` — the server's environment identity, protocol version, and
  capabilities. A session that receives a welcome for another environment, or
  for an incompatible protocol version, is blocked.
- `response` — the answer to one request, addressed by the request's `id`.
- `event` — an ordered server event, addressed by a monotonic `sequence`.

A request is one JSON object with an `id`, a `method`, and its `params`. The
method names are canonical and live in
[contracts](../crates/gitgui-protocol/src/lib.rs), which publishes them as
`WS_METHOD_NAMES`; the generator writes them into the TypeScript contract, and
[rpc/protocol.ts](../packages/client-runtime/src/rpc/protocol.ts) maps every
method to its payload and its result. A call is therefore checked against the
server's own definitions, and a test fails when the two lists drift apart.

A session is ready once the welcome arrived and the server described itself.
A probe answers with `server.get_status`.

## The session's own rules

The session owns the request lifecycle, because the envelope has no framing of
its own:

- A request registers a pending entry, and the entry is removed on every exit:
  a response, a rejection, a timeout, an interruption, or a failed write. A
  closing session refuses new requests rather than registering them.
- Opening the socket and completing the handshake are separate stages, and the
  welcome has its own deadline. A server that accepts the socket and never
  greets fails the handshake instead of hanging the connection.
- The first reason to end the session wins. A deliberate block, such as an
  incompatible protocol version, stays blocked when the socket closes after
  it, so the supervisor does not retry the environment as a transient failure.
- The reader always reports the end of the session, and closing the scope
  closes the socket and clears the pending requests.
- The event stream is lossless and ordered, and the server's monotonic event
  sequence is watched. A hole is reported as a gap so the consumer can
  resynchronize, and the publication never blocks, so a slow subscriber
  cannot delay an RPC response on the same connection. Every consumer has its
  own scoped subscription. The promise client disposes its readers when its
  workspace is replaced; the session closes all subscriptions on shutdown.

## Authentication

Loopback is not authentication. Local and remote backends use the same session
model.

- The desktop shell creates the primary bootstrap credential and keeps it in
  the operating system's protected credential store.
- The client exchanges a bootstrap or pairing credential for a scoped bearer
  session through `POST /oauth/token`, retaining the server's credential grant.
  Bootstrap sessions include repository catalog management so the desktop can
  open/create/remove repositories; ordinary pairing sessions remain limited to
  reading and operating on repositories already available on the host.
- The client asks for a short-lived, single-use WebSocket ticket through
  `POST /api/auth/websocket-ticket` and puts it in the socket URL.
- Every RPC method is authorized against explicit GitGui scopes by the server.
- Every connection preparation also reads `GET /api/auth/session` using that
  connection's bearer header, after endpoint identity verification and before
  issuing its WebSocket ticket. This read bypasses the browser HTTP cache.
  The returned environment ID must match. Only
  the granted scope strings travel through the prepared connection into the
  RPC session and `EnvironmentWorkspaceView.sessionScopes`; no bearer secret,
  ticket, or authorization response is added to UI state or persisted metadata.
  Primary, hosted browser, direct/Tailscale, and forwarded SSH endpoints all use
  this same path. Anonymous development sessions use the server's explicit grant.
- Durable tokens never appear in URLs, logs, generated bundles, crash reports,
  or ordinary desktop settings. Non-secret catalog records and credentials use
  separate backend operations; Electron protects credentials through its native
  bridge, while the browser uses separate origin-scoped credential storage.
- Discovery strips browser fragment credentials from history and retains them
  for authentication within the application layer. Existing bearer sessions are
  validated directly, including cached primary sessions; bootstrap and pairing
  credentials are exchanged. A primary session rejected after a server restart
  can use the desktop's current bootstrap grant. Permission and transient
  failures do not trigger credential exchange.
- SSH verifies the prepared environment identity, reuses a valid saved bearer,
  and issues/exchanges a one-time OS-owner pairing grant only for a missing or
  rejected bearer. Pairing is independent of launch and also works on reuse.
  Its repository-management scope does not include access administration. Permission failures
  and transient failures remain classified for the supervisor. Disconnect uses
  the complete SSH target (host, user, port, and identity file), so cleanup
  reaches exactly the bridge that was prepared.

### Repository management availability

Advertised `repositories.open`, `repositories.create`, and `repositories.remove`
capabilities describe server implementations, not a client's permissions. Each
action requires a connected environment, its corresponding capability, and the
current authenticated session's `repository:manage` scope. Home projects Open and
Create for the chosen operation environment and Remove for each catalog location.
The path dialog and Create form recheck their pinned environment and show an
explicit reason when disconnected, unsupported, unknown, or denied. They keep
per-environment catalog loading and pending Create operations independent.

`rpc/client.ts` resolves the current session at execution time and refuses these
three management calls when its scope is absent or unknown. This is an availability
guard; the Rust server still authorizes every request. Empty scopes mean a known
grant with no permissions; absent/null scopes mean authorization is unavailable.
Neither case grants management. Session loss clears the projected grant, and a
replacement session supplies a fresh grant along with the normal generation
change. Grants are never restored from cached catalogs or inferred from desktop,
primary, SSH, or pairing credential types. A failed session-state read follows
the existing supervisor error/retry classification and cannot install a grant.

Registered repository selection still uses `repositories.get_snapshot`. Exact
known worktree paths continue to resolve to their environment's registered IDs,
so read/operate pairing remains useful without catalog management. Unregistered
paths and aliases requiring `repositories.open` still need `repository:manage`.
This change adds no RPC, protocol, server, Electron IPC, or SSH process behavior.
Scopes are read per connection attempt, not polled on an otherwise healthy session;
server-side authorization remains the authority for revocation and expiry.

The discovery and authentication surface is:

```text
GET  /.well-known/gitgui/environment
GET  /health
GET  /ready
POST /oauth/token
GET  /api/auth/session
POST /api/auth/websocket-ticket
GET  /ws
```

## The Svelte adapter

The runtime is framework-independent TypeScript. The web application mounts it
once at the application root in
[runtime.ts](../apps/web/src/lib/connection/runtime.ts), and the platform
services it needs live in
[platform.ts](../apps/web/src/lib/connection/platform.ts). Routes and
components never own sockets, retries, credentials, Electron detection, or SSH
behavior.

The workspace layer still speaks promises, so the runtime exposes one
promise view of the Effect session in
[rpc/promise.ts](../packages/client-runtime/src/rpc/promise.ts). That file is
the only bridge between the two worlds, and it is marked as such.

The shared runtime also provides framework-independent checkout references,
repository grouping and pure tab transitions in
[workspace](../packages/client-runtime/src/workspace/index.ts). These are the
first building blocks for the proposed multi-environment workspace; the web
adapter still selects one environment and its existing workspace remains the
authoritative tab owner. The grouping input does not yet come from server
catalog identity metadata. Switching an existing worktree now rejects a target
already open in another tab rather than removing that tab.

The web adapter projects a separate lightweight repository catalog for each
registered environment. Each catalog follows its supervisor's session and
loads through `registry.run` and the environment-scoped request function;
it does not select an environment or own retries. It retains the last successful
result on disconnect, distinguishes an empty successful catalog from an initial
failure, and cancels/ignores an old read on session replacement or removal.
The latest non-secret summary is cached separately by environment; removal
clears that cache. Successful local catalog mutations schedule a refresh of the
originating environment. The home view does not yet consume the projection.

Healthy foreground wakeups also revalidate repository catalogs. The web adapter
consumes the existing `ConnectionWakeups` stream, coalesces focus/visibility/resume
bursts, and reads every environment with a live session, including environments
with no tabs. Foreground refreshes share one request per environment/session;
replacement sessions and explicit post-mutation refreshes supersede old reads.
The wakeup reader is interrupted on
stop, and removal cancels only the removed environment's pending read. Catalog
failures retain the last snapshot and never initiate transport retries.

An application-wide tab metadata adapter can validate and migrate the older
per-environment tab records without deleting them. It is not yet wired into
startup and does not compete with the current workspace as a tab owner.

The adapter consumes the registry's `followStream` for both supervisor state and
sessions, including replacement of the entire supervisor. Saved selection waits
for asynchronous registration. Switching environments interrupts old watchers,
disposes old workspace/event readers, and invalidates asynchronous activation.

Catalog records retain profiles for every saved or learned route. Updates share
a catalog lock across environments. Earlier records containing inline credentials
are moved to the credential backend and rewritten without the secret. Explicit
removal clears the credential, registration, profiles, and environment workspace
metadata while leaving other environments intact. Disposed workspaces cannot
rewrite metadata after a delayed load.

Each explicitly added direct or SSH route gets an independent persisted
connection ID. Adding a different address to the same environment retains the
previous routes; the registry still deduplicates repeated addresses. SSH route
identity includes the identity file, matching the desktop manager, so different
keys for the same host/user/port remain separate options.

Selection has one source of truth in its separate client setting. Catalog
writes never replace it with a stale catalog snapshot; removing the selected
saved environment clears it. If removal fails while the session remains
registered, the adapter reattaches its workspace. A failed catalog write does
not delete the credential first. The desktop store writes a cloned candidate
state and publishes its cache only after the atomic file replacement succeeds.
Failed writes or renames leave cached registrations and credentials intact, and
later mutations start from the last committed state.

HTTP error bodies are validated before classification. Empty or nonstandard
401 bodies remain authentication failures without a schema defect. The HTTP
deadline covers the complete request, success/error body read, and JSON/schema
decoding. A peer that sends headers and stalls its body cannot block discovery
polls indefinitely; timeout interrupts and aborts the body read.

The server's CORS allowlist includes Effect's default `b3` and `traceparent`
request headers, following T3 Code's `apps/server/src/httpCors.ts`. Both the
Electron renderer and hosted browser client enforce preflight checks, including
for discovery. Only configured client origins are allowed. Node-based live
tests do not enforce browser CORS; the server regression test exercises renderer
preflights for discovery, token exchange, and WebSocket tickets.

SSH authentication cancellation/rejection and host-trust cancellation/rejection
are blocked failures requiring external action. The preload reconstructs typed
categories from bounded IPC results; diagnostic text is not the classification
contract. Network failures remain
transient. Cancelling a prompt therefore does not start a repeated prompt loop.
An explicit retry asks the supervisor to attempt the connection again.

## Desktop-managed SSH acquisition

The scoped SSH source set is pinned separately from the client runtime; see
[source compatibility](ssh-source-compatibility.md), [host runner](ssh-host-runner.md)
and [host authentication](ssh-auth.md). The Rust helper contract is private and
versioned independently of Git RPC. Normal descriptor/auth/Git traffic continues
directly over HTTP/WebSocket to the locally reserved loopback forward.

The shared onboarding service verifies a temporary authenticated RPC welcome and
initial info response before persistence. Electron atomically replaces the
non-secret registration and its protected credential. New registrations are
durably staged disabled, the host acquisition is claimed, the record is enabled,
and ownership is handed off before the ordinary supervisor is published. This
commit/activation boundary is masked against interruption. Failed claim leaves
a disabled record that can be retried or removed, including after restart.

The gateway installs a scope finalizer before its first IPC call, using a UUID
reserved by the renderer. Interruption therefore cancels actual desktop work
even if no launch result was received. Successful ownership handoff disarms the
temporary scope. A replacement RPC connection claims and takes ownership before
releasing the prior handle for that connection ID; a failed attempt preserves
the old handle. This does not add a reconnect loop. The supervisor remains the
only retry owner, and uncertain mutations are never replayed.

Cancellation and explicit-disconnect IPC have a 20-second outer budget, enclosing the desktop's bounded
host cleanup and local tunnel termination. Lost replies/rejections report
`cleanup-pending`, and shared resources can report `retained`; settings display
the outcome without claiming observed remote exit. Desktop journals retain the
non-secret acquisition/instance/locator information needed for reconciliation.

Saved SSH profiles retain an explicit canonical remote data-directory locator
after identity validation. Old profiles use the exact legacy key only to locate
their existing directory; conflicting identity or unverifiable old ownership
blocks instead of launching against another catalog. New routes use the ordinary
per-user environment, independently of SSH alias, port or identity-file changes.
EnvironmentId and ConnectionId retain their existing meanings.

Settings also exposes optional existing-directory recovery. It requires the
saved environment ID before acquiring that directory, and carries the expected
identity through onboarding so a mismatch fails before credential exchange.
This selects existing state; it does not establish ownership of a pre-helper
process whose ownership evidence is missing.

Discovery/auth JSON is schema-decoded from a bounded 256 KiB stream; redirects
are rejected, and deadlines include headers and body consumption. A descriptor
and the saved expected identity must agree before any credential is sent or a
new pairing grant is requested.

For the primary restart regression, build the Rust binary and run:

```sh
cargo build -p gitgui-server
GITGUI_IT=1 npm run test -w @gitgui/web -- src/lib/connection/restart.live.test.ts
```

This opt-in test uses real servers with isolated persistent state and a desktop
bridge fixture. It verifies automatic crash recovery, explicit restart onto a
new port, and reopening with cached credentials. It stops only its own server
processes. It does not exercise Electron itself or a real SSH transport.

## Application workspace coordination

The framework-independent `WorkspaceTabCoordinator` provides serialized,
persist-before-publish tab transitions and short-lived canonical checkout
reservations. It accepts a resolver and preparation callback so network work
does not block unrelated tab commits. Closing a source or removing a target
environment invalidates pending transitions. The web metadata adapter migrates
legacy tabs across environments, retaining tabs for registrations that arrive
later. `ApplicationWorkspace` is mounted by the Svelte workspace adapter with
external tab ownership. It is the sole tab writer; environment data services
project its targets without persisting competing open/active lists. The default
legacy mode remains available to older adapters and tests.

## Environment workspace data

`WebApplicationRuntime` now maintains one `EnvironmentWorkspaceData` for every
registered environment, including environments with no selected UI tab. Its
`environmentWorkspaces` getter (also included in subscribed state) exposes each
service's `client`, `workspace`, `workspaceState`, `welcome`, `generation`,
`ready`, `loading` and `error`. `getEnvironmentWorkspace(environmentId)` returns
the stable service, or `undefined` after removal. The getter is always populated;
the subscribed-state field is optional in its type for legacy state adapters.

The registry's `followStream` owns state/session following, including whole
supervisor replacement. Each data service keeps a stable Promise client and
workspace. Calls capture their environment and input, then resolve the registry's
current session once at execution. Session loss/replacement interrupts pending
local waits, invalidates workspace reads and switches event/gap readers. Event
sequence state and capabilities reset per session; delayed welcomes and read
results cannot overwrite a replacement or resurrect a removed environment.
An uncertain mutation is never replayed. Only the supervisor retries transport.

Legacy metadata is restored as ID placeholders before network hydration. Offline
state retains tabs, recents and hydrated data. Rehydration refreshes summaries
and snapshots independently for each environment, even with equal repository
IDs. Removal disposes only its service after the registry commits removal;
failed durable removal leaves it usable. Stop disposes every service and reader.
The service generation is an invalidation counter for loss/replacement, rather
than a copy of the supervisor's connection-generation number.

The repository presentation passes that scoped service generation to commit-file
and file-diff readers once the session welcome and capabilities are installed,
using zero to invalidate reads/reviews while unavailable. A stable client object
is not a read identity: replacement
must retry an unchanged selection and reject late responses from the old read.
Hunk reviews and selected hunks are invalidated on generation changes, even if
the replacement returns identical contents. Restored tabs without a snapshot
show their owning environment's availability and scoped retry; connecting and
hydrating placeholders remain loading states. Retry requests the supervisor for
an unavailable environment or refreshes that repository on a healthy session.

The default constructor preserves legacy tab persistence. Its selected
`client`, `workspace` and `workspaceState` fields are compatibility projections;
selecting another environment no longer disposes data. Initial compatibility
publication waits for hydration, while the scoped API exposes offline placeholders
immediately. A completed workspace remains projected across subsequent loss.

The application-tab integration constructs the runtime with
`new WebApplicationRuntime(options, { tabOwnership: "external" })` (or pass
those arguments to `provideWebApplicationRuntime` at the Svelte root). After the
single application coordinator publishes its tabs, group their repository IDs
by EnvironmentId and call
`await runtime.getEnvironmentWorkspace(id)?.setRepositoryTargets(ids, activeId)`
for each environment (including an empty list when its last tab closes). Equal
projections are no-ops. This attaches data readers without persisting a tab list.
Dropping reader targets aborts pending workspace reads and prefetch hints; closing
the last target leaves the registration and catalog alive. External mode rejects
legacy open/select/close tab operations and preserves the
old metadata's tab fields when saving recents. Prepare repository opens through
the captured service's `client` or `requestEnvironment`, commit them through the
one coordinator, then publish targets.

The Svelte workspace adapter supplies these projections and uses scoped routes
and per-target UI state. Actions capture their service and checkout and use
that target's current welcome/registry state. Regression coverage is in `connection/runtime.test.ts`
and `client-runtime/workspace.test.ts`.

### Application workspace review fixes

`ApplicationWorkspace` retains each open/create/switch response privately until
the coordinator durably publishes its tab. Publication supplies the prepared
summary and snapshot to that environment's reader projection. Failed metadata
writes, aborted navigation, or session replacement discard the private response;
later hydration failures retain published data. External offline targets seed
their summaries from the environment catalog cache, including missing/worktree
metadata. Changing only active selection keeps healthy readers and avoids a
catalog refresh. Replacement target hydration owns readiness when it cancels
initial activation reads.

Exact registered host paths resolve through their scoped repository IDs and
snapshot reads; only unknown paths use `repositories.open` and its management
scope. `switch(tabId, target, expected, signal?)` and
`switchPath(tabId, path, expected, signal?)` accept navigation cancellation.
`closeIfMatches(tabId, expectedTarget)` compares the target inside the serialized
tab commit, so a delayed repository removal cannot close a switched checkout.

Removable registrations write `gitgui.applicationWorkspace.removals.v1` before
registry removal. Catalog deletion is the removal commit point: credential
deletion can fail afterwards, leaving a committed removal and a stale in-memory
entry. A rejected removal therefore retains its intent. Startup passes all
pending intents to recovery without inferring completion from hydrated memory.

`EnvironmentRegistry.recoverRemoval` reads the current persisted targets under
the same environment lease as register/remove. A surviving or replacement
registration cancels the old intent without deleting its credentials, cache,
metadata or tabs. Otherwise recovery closes any stale session, releases SSH,
retries credential deletion and owned-data cleanup, then runs tab persistence
and journal acknowledgement under that lease. Re-registration waits for this
completion, so it cannot publish new tabs between the presence check and tab
deletion. The catalog writer also holds its lock through credential deletion,
preventing an old removal from deleting a newly registered credential.

Primary discovery never creates an intent, and disappearance alone does not
authorize cleanup, so late or temporarily absent primary tabs survive. Failed
tab or owned-data persistence stays pending and retries after one second; the
journal survives restart until all cleanup and acknowledgement succeed. A new
registration retires a stale intent and releases the application's open guard.
Unreadable or malformed catalog records fail recovery rather than proving
absence; legacy empty-route records still count as saved registrations.
This is GitGui-owned recovery across its registration and tab stores, not a
second connection retry owner. A failed intent write prevents removal.

SSH disconnect runs before fallible owned-data cleanup, including when catalog
deletion committed before credential failure. A rejected gateway disconnect
retains the old profiles for retry. Electron still owns exact acquisition IDs,
forwards and remote process-instance ownership; it releases only its own handles
and retains external/shared servers. Host loss or a lost IPC response is reported
as cleanup pending, with the desktop's non-secret SSH ownership journal retained
for reconciliation on the next connection to that host. Workspace-journal
completion does not assert remote process exit.

Limitations: the browser keys and protected desktop store are not one atomic
transaction; cleanup is idempotent and may be partially applied before retry.
The lease serializes one runtime's writers; cross-window/process writers do not
have a distributed transaction. Recovery needs readable persistence and a
mounted application workspace. Remote SSH cleanup has no background sweeper
when the host remains unreachable or is never connected again.

passed 125 tests (one existing skipped test), and its TypeScript check passed.
The focused web runtime/platform/application-workspace suites passed 98 tests,
including restart, durable/memory disagreement, read failure, re-registration,
credential and cleanup failure, tab write failure, and late primary retention.
The SSH manager lifecycle suite passed 22 tests covering acquisition ownership,
independent environments, retained/external servers and journal reconciliation
after restart. Svelte validation reported zero errors and the existing
`WorkingTreeFileList.svelte` accessibility warning; the production web build and
`git diff --check` passed. The build also reported existing bundle-size and
Rollup annotation warnings. Reviewed adaptation hashes match the manifest;

Watcher-driven repository summary changes update only their owning catalog and
