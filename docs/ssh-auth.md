# SSH host authentication

The managed server uses `AuthStore::open(environment_id, bootstrap, data_dir)` on a blocking startup worker after loading the durable `server.json` identity. Unlike `AuthStore::new`, this always requires authentication, even with no bootstrap or existing grants. `open` persists that requirement in the independent `auth-required.json` policy marker, bound to the environment ID. Deleting `auth.sqlite3` therefore does not turn the managed server into an anonymous server: a missing database under that policy, a missing policy marker beside an existing database, or a corrupt database or policy marker, fails startup closed. Existing databases with missing metadata, including truncated files, are never reinitialized. Both files were introduced together by this unreleased durable format; there is no implicit database-only migration. Use `AuthStore::new` only for the explicitly anonymous standalone development mode. The primary bootstrap remains reusable for the process lifetime.

The host runner calls `AuthStore::issue_owner_pairing(data_dir, expected_environment_id).await` after authenticating the OS owner over SSH. It requires a matching existing `server.json` and issues a single-use, ten-minute credential with repository read, operate, and manage scopes, never access write. Deliver the result through the protected SSH channel, without logging or putting it in command arguments. Ordinary authenticated direct pairing retains `CLIENT_SCOPES`. The helper must only be exposed to the owner of the selected data directory; this function does not itself authenticate the caller.

`auth.sqlite3` contains a persistent random digest key and keyed digests rather than bearer or pairing tokens. On Unix its file mode is restricted to 0600. Protect the data directory and its backups with OS permissions as well; Windows ACL hardening remains the host installer's responsibility. Every authentication-repository operation validates the stored environment ID and digest key inside its SQLite transaction before reading or changing grants and sessions. SQLite transactions serialize grant consumption with session creation across processes. Sessions survive restart and can be revoked by token through `revoke_session`; WebSocket tickets remain process-bound. Missing or corrupt database metadata fails closed. The policy marker and database key are separate files: the marker preserves the authentication-required decision if the database is deleted, while the key and database remain in the database file. This limits accidental token disclosure but does not protect against an OS user who can read or replace the protected files.

This translates T3's durable pairing/session repositories and independent CLI issuance to SQLite and GitGui's existing opaque tokens. T3's signed token representation and metadata-rich session administration are not copied. Wire contracts and endpoint integration remain the caller's responsibility. Map `AuthError::Storage` to a generic server error and `IdentityMismatch` to a non-secret failure; never log credentials.
